# MailDev Server Requirements

## Scope and Decision Status

Source: [PM intake](../intake/maildev-server.md). This package is analysis and planning; no server, protocol support, API or acceptance test is implemented. IDs below are scoped to `maildev-server`.

The user confirms **phase 1** captures and inspects email for development, exposes a POP3 server for external mail clients, and **a later required phase** adds real outbound email via SMTP and API after capture/inspection works. POP3 retrieves mail; it does not send. Polling an upstream POP3 server is outside confirmed scope. External delivery is a required future capability, but its transport (smarthost or direct MX), operational policy and deployment activation require explicit decisions. A sending API must distinguish local capture from real delivery; accepted never implies externally delivered.

Existing [.NET platform requirements](dotnet10-platform.md) and its [tasks](../plans/dotnet10-platform/Tasks.md) are prerequisites. One .NET 10 monolith hosts Razor Pages, API controllers and protocol listeners with N-Tier boundaries. Database/storage/cache provider choices remain as already planned. Specific mailbox models, authentication, retention, limits and endpoints require approval before their implementation.

## Functional Requirements and Acceptance Criteria

All ACs describe **future behavior**. Phase 1 requirements are binding for the capture system and POP3 server; real external delivery is required in a later gated phase. Upstream POP3 polling and UI remain conditional additions outside confirmed scope.

| ID | Requirement | Given / When / Then acceptance criterion |
| --- | --- | --- |
| REQ-001 / AC-001 | Protocol selection and delivery policy | Given the agreed capture or external-delivery mode and POP3 direction, when the host starts, then only configured listeners/adapters start; an invalid or incomplete active configuration fails startup with redacted diagnostics. No implicit external relay or upstream polling occurs. |
| REQ-002 / AC-002 | SMTP ingress and envelope | Given an allowed SMTP session, when a client submits a valid sender, one or more recipients and DATA within limits, then the listener validates command sequencing, records envelope sender and accepted/rejected recipients separately from message headers, and accepts only the recipient subset allowed by policy. Invalid sequencing, malformed addresses, rejected recipients or oversized input produce appropriate non-success replies without creating deliveries for rejected recipients. |
| REQ-003 / AC-003 | Durable capture and visibility | Given a completed SMTP DATA submission, when the server returns success, then durable raw message bytes and metadata/mailbox delivery records have been committed and remain available after process restart. If storage/commit fails, it returns temporary/permanent failure as appropriate, leaves no visible partial delivery, and recovery/reconciliation handles any orphaned blob. A repeated client attempt after ambiguous connection loss may create a duplicate unless a documented idempotency mechanism applies; never promise exactly-once SMTP. |
| REQ-004 / AC-004 | MIME and attachments | Given a multipart message with attachments and non-ASCII content, when it is captured, then its raw RFC 5322/MIME form is retained and an authorized user can retrieve raw content and permitted attachments without silently altering bytes. Parsed subject, headers and body are derived views; malformed content and unsupported encodings return safe, documented outcomes. |
| REQ-005 / AC-005 | POP3 server | Given an authenticated mailbox and a stable session snapshot, when a client uses USER/PASS or approved authentication, STAT/LIST/UIDL/RETR/DELE/RSET/NOOP/QUIT, then response syntax, octet counts, CRLF and dot-stuffing follow the documented supported RFC subset. UIDLs remain unique within a mailbox and stable for the lifetime of each retained delivery. DELE marks messages for the session, RSET clears marks, successful QUIT commits deletions, and disconnect before QUIT does not commit them. CAPA advertises only actually supported capabilities. |
| REQ-006 / AC-006 | Mailbox isolation and concurrency | Given concurrent clients, when two sessions attempt to update the same mailbox, then only one acquires an exclusive mailbox transaction at a time, including across replicas; conflict is rejected cleanly. A mailbox cannot list, retrieve or delete another mailbox's deliveries. Define interactions with API deletion and crash recovery so sessions and UI never expose partial updates. |
| REQ-007 / AC-007 | API read and manage | Given an authorized API caller, when it lists, filters and pages messages, reads metadata/raw content or downloads an attachment, then responses conform to documented DTOs and authorization, stable pagination and limits. Missing IDs return documented errors without disclosing other mailboxes; unsafe cookie-authenticated operations require explicit CSRF protection. Scalar describes controller routes and errors, not SMTP/POP3. |
| REQ-008 / AC-008 | API submission / send | Given an authorized caller, when a valid message with recipients is submitted, then it enters the agreed capture or delivery workflow with a stable submission ID and documented asynchronous/synchronous status. Invalid, unauthorized or oversized requests return a clear failure. Capture-only mode stores locally and explicitly reports no external delivery; no public open relay is created. |
| REQ-009 / AC-009 | Protection and operational controls | Given an enabled listener or API, when credentials, message payloads or attachments are processed, then configurable connection/message/recipient limits, timeouts, least-privilege authorization and redacted logs apply. Sensitive commands and content are not logged by default. TLS/authentication policy is explicit per endpoint, required for untrusted networks, and uses validated certificates; insecure local development cannot be enabled accidentally in production. |
| REQ-010 / AC-010 | Deployment and configuration | Given valid Docker or k3s/k8s configuration, when the monolith starts and stops, then separate configured SMTP, POP3 and HTTP listeners start within the same application process, readiness reflects required dependencies/listeners, and shutdown stops accepting new sessions and drains within an agreed timeout. TCP ports are exposed via suitable Services/ingress, not assumed to flow through HTTP ingress. Secrets enter via environment/approved secret provider, not images. |
| REQ-011 / AC-011 | Provider and replica safety | Given a supported database/storage/cache combination, when messages are delivered concurrently and instances restart, then durability, isolation and POP3 mailbox locking satisfy the contract across all supported replicas. PostgreSQL/shared blob storage and a verified distributed lock or DB transaction are planned for multi-pod. SQLite and node-local volume are not assumed safe shared multi-writer storage; single-replica constraints are explicit. InMemory cache is never the source of truth or distributed lock. |
| REQ-012 / AC-012 | Quality and protocol evidence | Given an implementation, when QA tests it, then conformance is reported only for the named commands/extensions and RFC requirements actually exercised; interoperable SMTP/POP3 client integration, boundary/security/concurrency/restart tests, and ≥80% aggregate production executable line coverage pass. Dev follows TDD/SOLID/OOP; QA then SEC precede DocKeeper. Missing infrastructure or coverage is blocked, not a pass. |
| REQ-013 / AC-013 | Outbound external delivery via SMTP and API, required later phase | After phase 1 acceptance and an agreed activation/security policy: given an authorized outbound request submitted through either SMTP or API, when the selected delivery transport processes recipients, then per-recipient queued/delivered/deferred/failed outcomes, bounded retries and failure diagnostics are durable and truthful. Appropriate authentication, TLS verification, audit, rate limits and recipient/relay restrictions prevent open relay; no exactly-once or delivery-to-inbox guarantee is implied. Choose direct MX versus smarthost and define bounce/DSN policy before implementation. |
| REQ-014 / AC-014 | Upstream POP3 retrieval, outside confirmed scope | Only if separately requested: given an authorized configured upstream mailbox, when a polling worker retrieves mail, then TLS/authentication is validated, UIDL-based checkpoints and durable idempotency avoid duplicate ingestion under retry, upstream deletion occurs only under an explicit post-durable policy, and disconnects or concurrent pollers recover safely. This is separate from serving local POP3 clients. |
| REQ-015 / AC-015 | Razor UI, conditional on agreed screen requirements | Given authorized use cases and an approved UI scope, when a user uses a Razor Page to browse or inspect a message, then it calls shared Application services, preserves API authorization and output encoding, protects forms with antiforgery, and renders untrusted HTML safely. No specific screens or live-update mechanism are assumed. |

## Proposed Contracts and Open Decisions

1. **Delivery mode:** phase 1 capture-only; phase 2 must add real SMTP/API sending after capture and inspection pass acceptance. Decide direct MX versus authenticated smarthost, recipients, throttling, queue/retry/DSN, audit and operations. Keep real sending disabled by default and do not send actual mail without explicit operational authorization.
2. **POP3 direction:** local POP3 server is confirmed. Define mailbox provisioning, credential mechanism, mapping accepted envelope recipients to mailboxes, and deletion/retention. Upstream POP3 polling is outside confirmed scope; define its policy only if separately requested.
3. **API use cases and identity:** agree who may submit, browse, read raw data, download and delete; define token/cookie policy and tenant boundaries. Specify endpoints and idempotency keys before implementation. UI scope and API request/response schemas are still to be agreed.
4. **Persistence model:** define storage keys, encryption, metadata versus raw/attachment layout, sizes/quotas, TTL/retention, backup/recovery, deletion semantics, and whether API delete is allowed during a POP3 session. For database plus object store, choose a staged-object plus transactional-metadata/reconciliation design with fault-injection tests; do not claim a distributed ACID transaction.
5. **Protocol profile:** agree supported command/extension set, listener bind addresses/ports, TLS mode and certificate rotation, auth mechanisms, message/address/recipient limits, SMTPUTF8/8BITMIME/PIPELINING support, failure/status mappings and interoperability targets. Advertise no unsupported extension. Choose local defaults explicitly; RFC-required ports are not assumed for a Docker dev setup.
6. **Operations:** decide privacy/retention, mail content redaction, deployment profiles, replica count, network exposure, readiness and graceful shutdown, rate limits, testing services, incident response and observability. Do not expose credentials or raw message contents in logs.

## Standards and Library Evaluation

Use [SMTP RFC 5321](https://www.rfc-editor.org/rfc/rfc5321), [POP3 RFC 1939](https://www.rfc-editor.org/rfc/rfc1939), [POP3 CAPA RFC 2449](https://www.rfc-editor.org/rfc/rfc2449), [Internet message format RFC 5322](https://www.rfc-editor.org/rfc/rfc5322), [MIME RFC 2045](https://www.rfc-editor.org/rfc/rfc2045), and [email TLS RFC 8314](https://www.rfc-editor.org/rfc/rfc8314) as relevant references. They are baselines, not a claim of full implementation or conformance. Record the exact supported profile and independent tests; check updates and applicable extensions at implementation time.

Before selecting a library, assess .NET 10 compatibility, server versus client role, advertised command/TLS/auth support, license, maintenance, concurrency, security advisories and integration-test evidence. [MailKit](https://github.com/jstedfast/MailKit) provides SMTP/POP3 **clients** and is a candidate for later outbound delivery, separately requested upstream use, and testing; it is not evidence of a server implementation. MIME parsing and server choices remain evaluation tasks.

See [PLAN](../plans/maildev-server/PLAN.md) and [Tasks](../plans/maildev-server/Tasks.md) for scoped design, phased execution and traceability. Status remains planned until actual implementation and QA/SEC evidence exist.
