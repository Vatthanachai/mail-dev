# Technical Feasibility Review: MailDev Server

## Status and User Decisions

This document reviews a proposed design and implementation approach. It does not claim that a listener, repository, provider, container, test, or mail delivery is implemented. The user has specified two phases: first receive/capture and inspect development email, then add real outbound delivery through SMTP/API after the first phase works. POP3 means this application exposes a POP3 server for external email clients to read messages. POP3 itself does not send messages. Direct-to-MX versus an authenticated upstream smarthost remains an open architecture decision for outbound; do not assume either one or silently enable outbound during phase 1.

## One Host and Protocol Boundaries

- Run Razor Pages, API Controllers and TCP listener hosted services inside the existing planned .NET 10 `MailDev.Web` host/process and one deployed image. Listener adapters translate protocol operations into Application use cases; Application defines interfaces, Domain carries invariants, Infrastructure implements transport/storage. Do not put business logic or persistence SDKs in the Web layer. `BackgroundService`/`IHostedService` can participate in host startup and shutdown; supervise listener failures and expose accurate readiness.
- SMTP accepts a session's envelope sender and accepted recipients separately from RFC 5322/MIME headers. Preserve accepted raw message bytes and relevant envelope metadata; never reconstruct the POP3 raw representation from parsed HTML or display fields. API and UI read the same authoritative message records. Keep decoded text, attachments and HTML rendering as projections; display untrusted content safely and preserve original content for retrieval.
- HTTP serves UI, API and Scalar; SMTP and POP3 require separate TCP listeners and explicit ports/exposure. Ports, authentication, TLS modes, domain/mailbox model, recipient policy and retention are not yet user-approved. In phase 1 accept/capture only; disallow routing mail to the public Internet even if configuration is malformed.
- API send in phase 2 initiates a durable outbound workflow, with status separate from success of external delivery. SMTP submission in phase 2 must use explicit authenticated/authorized policy, recipient checks, rate/resource limits and audit; it must not become an open relay. Decide if API submission and SMTP submission share the same outbound queue and policy, and define partial delivery, retry/backoff, idempotency, failure/DSN, bounce-loop handling and retention before coding. Never promise exactly-once external delivery.

## SMTP and MIME Durability

Use bounded streaming/spooling, not unbounded message-in-memory buffering. Validate line/message size, command sequence, recipients, concurrent connections, per-connection idle and total timeouts; reject malformed/over-limit input at the correct stage with SMTP-appropriate temporary/permanent responses. Limit decompression/MIME parsing resources and treat HTML/attachments as hostile. Advertise an extension only when fully implemented and tested, including correct STARTTLS capability renegotiation.

Proposed crash-consistent capture for selected DB and blob/filesystem storage: stream an immutable object to durable storage, verify its completion/availability, then transactionally commit message, mailbox associations and object reference in the database; send final SMTP success only after both are durable and recoverable. Fail with a temporary response if either durable stage fails, and retain enough staged-object metadata for safe orphan cleanup. Reads never expose a DB record whose object is missing; use reconciliation/alerts for storage outages. Test failures/crashes after each boundary, recovery, multiple recipients, and retries. Object storage and a relational database do not form one atomic transaction; cleanup must never delete referenced content.

An accepted message whose final response is lost may be retried, creating a duplicate. This is an at-least-once ambiguity, not exactly-once capture. Record any eventual deduplication policy explicitly; `Message-ID` alone is not a universally safe idempotency key. API idempotency can instead use an explicit client key with documented scope/expiry. Preserve reference counts or equivalent ownership when multiple mailboxes point at the same raw object.

## POP3 Semantics and Concurrency

Implement a POP3 server, not a client fetcher. Authentication grants access to one authorized maildrop, subject to explicitly defined credential/TLS policy. Implement and test AUTHORIZATION, TRANSACTION and UPDATE state transitions, response and octet framing, dot-stuffing, command limits and correct handling of invalid sequences. `DELE` marks messages within the session, `RSET` clears marks, and only a client `QUIT` from TRANSACTION commits deletion; disconnect or timeout must not commit. Error handling during UPDATE must not delete unmarked messages. Provide stable `UIDL` IDs per mailbox across sessions; identifiers must not be derived solely from message bytes when duplicates are distinct messages. See [RFC 1939](https://www.rfc-editor.org/rfc/rfc1939.html) and [RFC 2449](https://www.rfc-editor.org/rfc/rfc2449.html).

Create an ordered stable per-session mailbox snapshot and an exclusive mailbox mutation/POP3-session lock that protects the transaction from concurrent API, SMTP delivery, cleanup and other POP3 sessions, with a documented policy for arrivals during the session. For multiple pods, a process-local mutex or InMemory cache is insufficient: use an authoritative shared coordination implementation with lease expiry, fencing and atomic transaction checks so stale sessions cannot commit. Keep a clear failure behavior if lock ownership is lost. PostgreSQL-backed coordination is a candidate after proof; SQLite/node-local Volume should initially be restricted to explicitly tested single-replica topology. A network-mounted SQLite file or generic Redis cache does not automatically provide the required locking guarantees.

## Deployability and Operations

The same Docker image supports single-instance Docker and k3s/k8s deployments. A Kubernetes Service or ingress controller configured for TCP must expose SMTP and POP3 separately from HTTP; an ordinary HTTP ingress route alone does not forward those protocols. Keep bind addresses/listener ports and TLS certificate references configurable. Inject `.env` values for Docker; translate the agreed key names into Kubernetes ConfigMaps/Secrets or the approved secret mechanism instead of assuming `.env` is loaded by Kubernetes.

Define startup/readiness so traffic is accepted only when relevant listeners and required durable dependencies are usable; liveness should detect a stuck process without restarting it merely because a remote service is down. Stop accepting new sessions on termination, drain active work within a bounded grace period, and preserve the SMTP acknowledgment and POP3 deletion guarantees on interruption. Test TCP routing, persistent storage and connection draining in an actual supported cluster; treat local Docker tests as separate evidence. For multi-pod mode require shared authoritative PostgreSQL, suitable shared object storage and proven coordination; shared Data Protection keys are separately required for web cookie/antiforgery continuity. Non-root file permissions and certificate access must be verified.

## Verification Strategy and Acceptance Evidence

- Apply Red → Green → Refactor for each protocol/contract behavior. Maintain actual tests for raw wire transcripts and standard client interoperability, MIME nested parts, envelope/header distinction, CRLF, dot-stuffing, size boundaries, TLS/auth failure, connection limits and injection.
- Exercise SMTP storage/object/DB failure points, process termination before/after commit and before final response, retry duplicates and partial-recipient policy. Exercise POP3 UIDL persistence, concurrent clients, `DELE`/`RSET`/`QUIT`, aborted sessions, leases/fencing, API conflict and independent replicas.
- Test HTTP API authorization, selected phase's send semantics, non-leaky errors, raw/attachment streaming, pagination, UI encoding and isolated mailbox access. In phase 2 use a controlled SMTP sink/relay and fault simulation; avoid sending test email to real recipients.
- Cover PostgreSQL/SQLite and Volume/S3/Azure Blob contracts with isolated real services or emulators as available. Verify durable restart and multi-pod configuration separately. Capture emulator versus real-service limitations. Keep production-project aggregate line coverage ≥80%, including listener adapters and failure paths, with independent QA re-run and SEC before DocKeeper/PR.
